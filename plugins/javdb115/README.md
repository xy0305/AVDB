# JavDB sidecar dylib (AVDB115) v15

Standalone Objective-C dylib that adds AVDB-style **115 push/play**, **External Library**, and **HQ cover preview** to the official JavDB iOS app (`com.javdb6.com`). It does **not** change AVDB itself, and it does not hook JavDB membership, payment, or magnet APIs. The only intentional UI change on the official movie-detail page is two extra action chips, described below.

This folder is the only AVDB-repo addition on the isolated `ci/javdb-115-dylib` branch, together with `.github/workflows/javdb-115-dylib.yml`.

## What it does

- Floating “115” button (Flutter-safe: window / scene notifications plus delayed attach). On a detected movie detail page it is hidden so it is not the primary control; a less prominent **115 设置** chip (and iOS Settings) still opens the panel.
- Settings panel: 115 Cookie (Keychain, `ThisDeviceOnly`) and offline folder CID.
- **iOS Settings app** (`Settings.bundle` injected into `Runner.app`): 115 Cookie, offline folder CID, identified-ad toggle, external-library URL/token. The system Settings text fields write UserDefaults only. On launch / foreground the plugin migrates the 115 Cookie and external token into Keychain and **deletes the plaintext**. The Settings field will then look empty; that is expected and the values are not written back. Folder CID stays in UserDefaults. The floating-button panel remains the fallback (it reads Keychain). JavDB’s own Flutter settings page was not patched.
- **Identified ad blocking** (default on): no AdMob / Unity / Pangle / GDT / SKAdNetwork SDK was found. Ads are first-party (`/api/v1/ads`, `/api/v1/ads/splash_log`, Flutter `HomeAd` / `SplashAd`). Native hooks may cancel those API URLs on `jdforrepam.com` / `letidi.com` if they go through NSURLSession or `WKWebView loadRequest`. Home / magnet-page ads are Flutter-painted over dart:io TLS, so they usually cannot be blocked; **this build does not claim all ads are blocked**. Payment, auth, movie, cover, and 115 URLs are never blocked. Membership is not unlocked.
- **Opening splash ad (kai ping) attempt** (same Settings toggle): the iOS `LaunchScreen` is only the system launch storyboard (`LaunchImage`) and is left alone. The in-app ad is Flutter `SplashPage` (`package:astarte/main/splash_page.dart`, `_initSplash` / `_handleAd` / `_handleAdImage` / `_doCountDown` / `_goMain`). That page also does domain probe, update check, and local auth, so the whole route is not skipped. For about 20 seconds after launch the dylib calls `FlutterEngine ensureSemanticsEnabled` and, if a FlutterView accessibility control with a short skip label (`跳过`, `跳过 5`, `Skip`, …) appears, activates it once. The skip string `跳过` occurs once in App.framework. This is not Dart TLS MITM and does not hide the first window. **It has not been device-tested and this build does not claim the opening ad is removed.**

- **Movie-detail 115 chips — runtime Dart-row hook (v7), with v6 UIKit overlay fallback**: static analysis of JavDB 1.9.41 shows the visible 想看 / 看过 / 存入清單 row is assembled by Flutter `MoviePageState._getButtonLine` (`package:astarte/home/movie_page.dart`) into a `Wrap`. The fourth child is a `Consumer<MoviePageProvider>` (not a raw 離線觀看 chip). This build installs a 16-byte entry wrapper at `_getButtonLine` (FAT `0x3c1144` / VM `0x3bd144`) after verifying the 16-byte prologue. When the original function returns a `Wrap`, the hook allocates a length-6 Array, copies the existing four children, appends two cloned `MyInkWell` chips labeled **推送到 115** and **115 播放** after the Consumer, and updates the GrowableObjectArray. It does **not** replace 離線觀看, does **not** hook `getMovieMagnets`, and does not touch payment, VIP, or auth. Taps `dispatch_async` to the existing push/play actions. If the hook installs, the v6 UIKit overlay row is hidden (catalog/magnet scan continues; **115 设置** remains in iOS Settings and the floating chip). If the prologue does not match or `vm_protect` / `VM_PROT_COPY` fails, the hook is left uninstalled and the v6 overlay stays as the fallback. **This has not been device-tested.** Text-segment protect, Dart heap allocation, write-barrier abort, and C `sp` when entering from Dart remain hypotheses.
- **v6 UIKit overlay** (fallback only when the Dart hook is not installed): a second row of capsule buttons (height 32, pill radius, 13pt medium) is attached to the key window just above the bottom tabs when the page looks like a movie detail (catalog number from the nav title or「番號/番号」 field, plus those action labels). The chips are labeled **推送到 115**, **115 播放**, and a lighter **115 设置**. They do not cover 購買VIP, the cover play control, or the original four buttons. Flutter scroll would not reliably move a mid-page overlay, so the dock is stable rather than chasing the action row. **推送** reuses `addOfflineTask` on magnet/ed2k already visible in the FlutterView accessibility tree (or a confirmed clipboard link); it does not call `getMovieMagnets` or forge `jdsignature`. If no link is visible it can try to activate the 磁鏈下載 tab and ask the user to tap 推送 again. **115 播放** reuses the existing player with the bound catalog number (magnet optional).
- **One-tap 推送到 115** (v9): JavDB `MagnetListItem` shows `name` (e.g. `MIDA-859-U.LTX…`), an `ED2K` type badge, and `files_count`, not a raw `magnet:` / `ed2k://` URI. v7 only scanned accessibility labels/values for those URI prefixes, so a tap on an already-open 磁鏈下載 list could still show the “看不到磁力/ed2k” dialog. v8 reconstructs the same link as JavDB `Magnets.detailLink` (`buildMagnetLink(hash, name)` or the already-resident `url` for ed2k) from live `Magnets` objects (cid 2678) and already-materialized URI strings in process memory, filtered by the current catalog number. It then calls the existing `addOfflineTask`. It does **not** hook or call `getMovieMagnets`, forge `jdsignature`, or touch payment/VIP/auth. **離線觀看 is left intact.** If several links match, one catalog-matching magnet is preferred (then a matching ed2k). 115 播放 still searches 115 by catalog number and will pass a preferred magnet when one was found. v8 still missed already-open lists because it only walked 16-byte-aligned (old-space) addresses, required `Magnets` string fields to sit in the same `vm_read` buffer, and looked for raw `magnet:` / `ed2k://` text that `MagnetListItem.build` never materializes. v9 walks 8-byte alignment (new-space and old-space), reads string fields across heap pages, and also reconstructs links from already-resident JSON (`hash` / `name` / `url`). If the 磁鏈下載 list is already on screen and a link still cannot be parsed, the dialog no longer tells the user to open the tab first. This has not been re-tested as a successful device push; the v7 screenshot only showed that the list was already visible when the old scanner missed it.
- **v10 crash hardening (闪退 fix):** v9 could exit immediately when tapping **推送到 115**. The scanner kept a 96×16KB page cache (`AVDB115Mem`, ~1.5MB) as a stack local in `residentLinksMatchingCatalog`, which overflows the typical ~1MB iOS main-thread stack (`memset` on entry). v10 allocates that state on the heap, copies only through `vm_read_overwrite` into a single page-sized buffer (never dereferences a foreign pointer), follows string fields only when the address already sits inside an enumerated readable+writable region, skips empty / IOKit / guard regions, requires Magnets size tag 7 (rejects the loose size-tag-0 match), and caps the walk at 24MB / 0.15s. Failures return an empty list so the existing dialog is shown instead of crashing. One-tap reconstruction remains, but stability comes first. This has not been re-tested on a device.
- **v11 one-tap recovery:** a device run of v10 no longer crashed, but tapping **推送到 115** on an already-open 磁鏈下載 list (MFYD-211 row titles / ED2K / file counts, v6 overlay chips) still showed the “列表已在当前页，但仍未能还原 magnet/ed2k” dialog. Offsets and cid 2678 were re-checked against `Magnets.toJson` / `detailLink` and are unchanged. Two scanner bugs were fixed: Dart `String` length at untagged+8 is a **Smi** (`n << 1`), so v10 over-read a 40-char hash as 80 bytes and failed hex validation; and the 0.15s / 24MB walk skipped mappings larger than 512MB or with `pages_resident==0`, which can omit the reserved Dart heap (raw JSON may already be gone, and `MagnetListItem` still does not paint `magnet:` / `ed2k://`). v11 keeps v10 crash safety, decodes Smi lengths, searches first for the catalog number and visible row names (Latin-1 and UTF-16), follows tagged string pointers back to `Magnets`, and only then does a cid walk. It does **not** hook `getMovieMagnets`. This has not been re-tested as a successful device push.
- **v12 capture-at-load / capture-at-build:** a device run of v11 still showed the same “未能还原 MFYD-211 的 magnet/ed2k” dialog on an already-open「磁鏈下載 4」list (v6 overlay tap; no raw `magnet:` / `ed2k://` on screen). Re-checked AOT: `MagnetListItem.build` still loads `type` / `files_count` / HD from a live `Magnets` instance at tagged offset `0x0f`; `fromJson` writes `hash` (`0x1f`) and `url` (`0x67`) onto that object. The data is therefore in the widget graph while the list is visible — a tap-time process-wide heap scan is the wrong tool. Also, `Magnets.fromJson` is an instance initializer that **returns null** (`x22`); the object is `x1`. v12 wraps `Magnets.fromJson` (FAT `0xa03fc` / vm `0x9c3fc`) and `MagnetListItem.build` (FAT `0x57bacc` / vm `0x577acc`) with the same 16-byte prologue style as `_getButtonLine`, then `vm_read_overwrite`s the live object and caches official `detailLink` results (buildMagnetLink / existing ed2k url). **推送到 115** uses that cache first, then the v11 scan, then the existing dialog. `getMovieMagnets` is not hooked or called. App.framework dyld slide is taken from the `App` image (not `_kDartSnapshotText` alone, which can belong to Flutter.framework and would make a hook refuse to install). Overlay tap remains the fallback if a hook does not install, and still works if the cache was filled by the other hook. This has not been device-tested as a successful push.

- **v13 native intercept (no App.framework TEXT patch):** a freshly resigned v12 install still failed the same way (user: 「还是一样」) with the v11 “未能还原 … magnet/ed2k” dialog after opening「磁鏈下載」and tapping the **v6 overlay** chip. Every device screenshot from v7 through v12 still showed those bottom chips, so `_getButtonLine` and the same-style v12 `Magnets.fromJson` / `MagnetListItem.build` wrappers never installed (or never ran) on the resigned sideload. The honest cause is iOS W^X / code signing: `vm_protect` of App.framework’s executable segment is denied, so cache-at-load never filled and the fallback was the already-failed v11 heap scan. v13 does **not** make another App.framework entry-wrapper the primary fix. The list API is `GET {baseUrl}/api/v2/movies/{id}/magnets` (`HttpApi.movie_magnets`, base typically `https://jdforrepam.com`); `Magnets.fromJson` already stores `hash` / `url` / `name` / `type` from that JSON. The dylib now (1) hooks **NSURLSession** completion handlers and a pass-through **NSURLProtocol** for that path (ObjC, no TEXT `vm_protect`), (2) reads Dio **FileCacheStore** files already written under `http_cache` (and leftover `dio_cache.hive*`) after the user opened the list — CachePolicy in this IPA is `request`, so a body is only on disk if the response was allowed to be stored — and (3) does a crash-safe `vm_read_overwrite` raw UTF-8 scan for `"hash"` / `ed2k://` JSON in RW memory (Dio / dart:io buffers are not Dart String objects, so the v11 cid walk could miss them). Usable `magnet:` / `ed2k://` links are cached with official `detailLink` rules only (`buildMagnetLink(hash, name)` or an existing url). The overlay tap uses this cache first. **It does not hook or call `getMovieMagnets`, does not forge `jdsignature`, and does not invent hashes.** If restore still fails, the dialog adds a `[诊断]` line (NSURL hook / intercept cache / file cache / plaintext scan / object scan / App.framework hooks) so the next device test shows which path was empty. Flutter.framework has no NSURLSession symbols and uses statically linked BoringSSL with no DATA pointer to `SSL_read`, so dart:io TLS may be invisible to the session hook; file-cache + raw JSON harvest are the Dio-capable paths. A later device test of unsigned v13 confirmed one-tap push (user: 「可以推送了」). The v13 intercept / file-cache / raw-JSON path is kept unchanged in v14 and v15.
- **v15 catalog attribution:** a later device test on ROYD-360 (「磁鏈下載 4」already visible) failed with `拦截缓存=0 文件缓存=52 明文扫描=0 对象扫描=0 可用缓存=18` and App.framework hooks still 未安装. The cache *had* usable links; `linksForCatalog` only kept rows whose magnet `name` / URI contained the 番号, so titles whose file names omit `ROYD-360` did not match (v13 succeeded on a title like MFYD-211 whose names included the catalog). v15 keys magnets by the list-API movie id in `/api/v2/movies/{id}/magnets` (from the request URL, including a URL buried in a FileCacheStore record), maps id↔番号 from already-cached movie list/detail JSON (`id` + `number`/`code` in the same object), and when the 磁鏈下載 list is on screen also matches visible row titles or the newest unbound magnets response. It does not invent hashes, hook `getMovieMagnets`, or forge `jdsignature`. If usable cache is non-empty but the current 番号 still matches 0, the dialog now also lists `当前番号匹配` / `缓存番号` / `缓存影片id`.
- Push magnet / ed2k the **user already copied or shared** remains a fallback if no on-page / already-resident link can be parsed; optional push-and-play.
- Play via 115 original URL (m115 / 115driver MIT) with HLS fallback. Playback uses AVPlayer (JavDB has no KSPlayer).
- **v14 default landscape 115 playback:** `AVDB115PlayerViewController` (fullscreen black UIKit host, top-left 「关闭」, child `AVPlayerViewController`; this is the almost-black portrait chrome in the v13 device screenshot) now reports landscape as its supported / preferred presentation orientation, requests an iOS 16+ scene geometry update, and hooks `FlutterAppDelegate application:supportedInterfaceOrientationsForWindow:` only while this plugin player is presented. Official JavDB players are not forced. The v6 chips and the 115 FAB are hidden for the duration and restored on close, together with a portrait geometry request. A black picture area can still be a failed/empty 115 stream (original then HLS); orientation alone does not fix that. This has not been device-tested.
- **External database** (AVDB `ExternalLibraryClient`, not a local JSON file import):
  - Default root `http://163.47.40.207:8000` (already public in AVDB source), **disabled until the user enables it**.
  - User Token is stored only in Keychain as `X-API-Key`. Changing the server without a new token is rejected.
  - `GET /api/v1/articles/torrents?keyword=` with envelope `{data:[id,title,download_url,size_mb,seeders,chinese,uc,uhd]}`.
  - Root URL only; **all redirects are rejected**. No token in logs or UserDefaults.
  - Search / browse results in the plugin panel; magnet/ed2k can be copied or pushed to 115. The 115 Cookie is never sent to the external host.
- **HQ cover sources** in the same floating-panel menu:
  - Deterministic public URLs: DMM `awsimgsrc.dmm.co.jp` / `pics.dmm.co.jp` (Build 282 CID seed + 5/3-digit fallbacks), MGS Prestige/Jackson templates (`image.mgstage.com`).
  - Optional HTML: Avbase `https://www.avbase.net/works?q={番号}` `__NEXT_DATA__` (`image_url` preferred, then upgrade to awsimgsrc); JavBus first-party `/pics/cover/*_b.jpg` only.
  - Captcha, `driver-verify`, HTTP 403/429/503: skip the source, **no bypass**.
  - Preview + disk cache by 番号, timeout, cancel, URL dedupe, source fallback.
  - **v14 grid HD cover overlay (not a Flutter image rewrite):** Dart Dio / `dart:io` TLS still cannot be rewritten at NSURLSession, and App.framework / Flutter TEXT hooks still do not install on the resigned sideload (`vm_protect` RX→RWX denied). Official cover URLs remain `https://c0.jdbstatic.com/covers/{xx}/{uid}.jpg` (no catalog number). v14 instead installs a native, tap-through overlay that finds visible catalog numbers in the Flutter accessibility tree (homepage 「近期可播放更新」 and other movie grids with the same pipeline), estimates cover cells, and paints images from the existing `AVDB115CoverResolver` DMM/MGS (and other already-wired) HQ sources. Movie-detail hero images are not overlaid. The **替换原页封面** switch, default on, now arms this overlay; it is not a claim that original Flutter-drawn bytes were replaced. Alignment depends on the accessibility tree and may slip while scrolling; on failure the original cover stays visible. This path has not been device-tested.
    TPDB (user Bearer) and Tenhow actor mapping are not wired in this build.

Clipboard hooks only look for `magnet:` / `ed2k://` strings. Other clipboard content is ignored and never uploaded. The 115 cookie is not logged, not hardcoded, and not stored in UserDefaults (legacy UserDefaults values are migrated into Keychain and removed).

## Build (macOS + iOS SDK)

```sh
bash plugins/javdb115/scripts/build-dylib.sh dist/AVDB115-v15.dylib
```

GitHub Actions on this branch compiles `AVDB115.dylib` (packaged locally as `AVDB115-v12.dylib`) (arm64, iphoneos, install name `@executable_path/Frameworks/AVDB115.dylib`) and uploads it with a source zip. The workflow does not run on `main` and does not start AVDB app builds.

## Inject locally (unsigned IPA)

Do **not** put a JavDB IPA in this repository (the repo is public). On your machine:

```sh
python3 plugins/javdb115/scripts/insert_dylib.py ipa /path/to/JavDB.ipa dist/AVDB115-v15.dylib \
  -o dist/JavDB-1.9.41-AVDB115-v15-unsigned.ipa
```

The script copies the dylib into `Runner.app/Frameworks`, copies `Settings.bundle` into `Runner.app` (iOS Settings page), inserts `LC_LOAD_DYLIB`, and writes an **unsigned** IPA. It will not pretend to codesign. Sideload signing is a separate step you do yourself.

## Not verified

A device test of unsigned v13 confirmed one-tap 115 push from a visible 磁鏈下載 list (user: 「可以推送了」). That intercept / file-cache / raw-JSON path is unchanged in v14. Device install of v14 (landscape / cover overlay) and v15 (ROYD-360-style catalog attribution) have not been tested on a physical iPhone. External Library search with a live token, cover preview, splash-ad skip, and the movie-detail Dart-row hook remain unverified. v12 on a freshly resigned install still failed one-tap push (「还是一样」) with the v6 overlay visible, so App.framework `vm_protect` hooks are treated as not installed; v13’s primary path is native intercept / file cache / raw JSON, not another entry wrapper. A v11 run still showed the “未能还原 magnet/ed2k” dialog on an open MFYD-211 list; v10 no longer crashed; v9 was reported to 闪退; a v7 run showed the list was visible but the old scanner missed it. Whether the `_getButtonLine` entry hook installs under sideload (`vm_protect` + `VM_PROT_COPY`), whether the two appended chips render and handle taps, whether `ensureSemanticsEnabled` plus a `跳过` accessibility activate actually dismisses the Flutter splash ad, and whether the fallback overlay appears and stays aligned above the tab bar, is therefore unverified. AVPlayer may fail on some original 115 files; HLS is the fallback.
