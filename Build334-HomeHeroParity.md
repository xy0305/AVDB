# Build 334 — Home hero detail parity (taller hero, same proportion as detail)

Base: Build 333 / `ee29d26`, `feat/home-hero-detail-333`. MARKETING 1.0.2, build 334. Branch `feat/home-hero-parity-334`. Unsigned IPA: `AVDB-unsigned-1.0.2-334-home-hero-parity.ipa` (CI artifact `AVDB-334-release`).

This build was planned jointly with Muse and Kai after the user installed Build 333 and reported that the home cover's presentation still differed from the detail page's (「现在封面的发展和详情页的好像不一样」; a second report, that the detail page's back gesture was gone, the user then withdrew himself: 「手势返回还在」 — the custom gesture only accepts swipes starting within 26 pt of the leading edge, and Build 333 never touched MovieDetailView or navigation). Asked how to close the framing gap, the user picked: **raise the hero to the detail page's proportion** (「英雄区拉高，和详情页同比例」).

## Root cause of the remaining difference (from the 334 survey of Build 333)

333 made the hero paint the detail page's own display image (`art.image`), and the screenshot confirms the image and the bottom gradient are right. What still differs is the **frame**: the phone detail `portraitHero` is `min(width × 1.58, max(600, height × 0.8))` tall (≈ 616 pt at 390 pt wide), while the home hero was `clamp(width × 1.15, 430, 560)` (≈ 448 pt). The same portrait poster aspect-filled into the short home frame is cropped top/bottom; in the tall detail frame it is cropped on the sides. Same bitmap, different visible window — the face framing the user compared can never match.

## Locked plan (agreed with Kai and the user, implemented exactly)

1. **Phone hero height = the detail formula.** `HomeMetrics` gains the view `height`; `heroHeight` on phone becomes `min(width * 1.58, max(600, height * 0.8))`, textually and numerically identical to `DetailPortraitGeometry.imageHeight` (same width input: both are the full view width on phone). The hero now shows the same window of the poster as the detail page. Everything derived from `heroHeight` (ambient background, top scrim start, autoplay scroll gate, the 333 fade band and sheet edge, which are computed from the height) follows automatically. The 333 fade band (56 pt), the 32 pt overlap, and the raised bottom chrome are unchanged in absolute points. iPad keeps its 600 pt hero (the detail page's iPad geometry is a capped-width column, not full-bleed; out of the user's complaint scope).
2. **Fix the Build 333 test-target compile errors (found via the 333 CI logs).** Run 42986909710: release succeeded and `AVDB-333-release` was produced, but every job that builds `DetailPosterQualityTests` failed, because `HomeHero333Tests` called two helpers that do not exist — `HomeHero331Tests.render(width:height:)` with a trailing closure (the real `render` is positional and jacket-specific) and `HomeHero331Tests.heroMovie(...)` (no such member). The class now renders solids via `HomeHero332Tests.sRGBImage` and builds movies with the plain `Movie(...)` initializer. The app itself was never affected (the user ran 333 fine), which is why this is a test-only fix riding in 334.
3. **Tests / packaging.** `HomeHero334Tests` (hero height equals `DetailPortraitGeometry.imageHeight` at five phone sizes; iPad hero unchanged at 600). `scripts/test-home-hero334.py`; CI job `home-hero-334`; release regression list; `scripts/package-lut334.py`; artifacts `AVDB-334-*`. Prior 327–333 jobs stay (and should all go green again with the test target compiling). Marketing 1.0.2, build 334.

Out of scope (not touched): the detail page itself and its back gesture, home chrome layout besides the hero height, the 331/332/333 image pipeline, gestures and tap rules, tab bar, ONE, search.
