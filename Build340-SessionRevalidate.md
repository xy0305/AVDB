# Build 340 — detail auth errors revalidate the credential instead of dropping the session

Base: Build 339 / `fd581fc`, `feat/detail-glass-clear-339`. MARKETING 1.0.2, build 340. Branch `feat/session-revalidate-340`. Unsigned IPA: `AVDB-unsigned-1.0.2-340-session-revalidate.ipa` (CI artifact `AVDB-340-release`).

Context: on Build 337 the user logged in a second JavDB account, opened one movie detail page, the page showed its failure state （重试）, and the whole session immediately appeared logged out. The chain, confirmed by code audit: `MovieDetailViewModel.load()` sets `isAuthError = JavDBError.isAuthenticationFailure(error)` for ANY auth-class failure of the detail load — the classifier accepts HTTP 401, `JWTVerificationError` actions, and 「請登錄帳號」-style messages — and `MovieDetailView.reloadDetail()` then called `appState.markNeedsReauth()` whenever `vm.isAuthError && APIClient.shared.hasToken`. Since Build 335 the detail load includes token-carrying endpoints (search family, `may_also_like`) whose auth behaviour can differ per account: a second, lower-privilege account can draw an auth-class reply from a business endpoint while its credential is perfectly valid for the profile endpoint. One business endpoint's auth error therefore marked the ENTIRE session rejected — exactly what the user's own Build 327 principle forbids ("one business endpoint returning a JWT error does not prove the credential is globally invalid"). The token was retained, but the user saw a dropped login, and by 327 design nothing revalidates on foreground return.

## Changes

1. **`AVDB/AVDBApp.swift` — new `AppState.revalidateCredential()`.** The profile endpoint is the single arbiter of session validity again. The method no-ops when there is no stored token (same `activeToken ?? readToken()` non-empty pattern as `markNeedsReauth`), when `sessionStatus == .needsReauth` (already marked; 327 leaves recovery to manual re-login / cold launch), or when a check for the same token is already in flight (a dedicated `revalidation` slot — `restoreTask` is not hijacked). Otherwise it runs ONE `fetchProfile()` attempt — no retry burst — capturing the current token and epoch first; a result that lands after the token changed or the epoch moved is ignored, in the same guard style as `resumeValidation`. On success it saves the profile and lands on `.validated`. On failure it calls the existing `markNeedsReauth()` ONLY when `JavDBError.isAuthenticationFailure(error)`; any other error (network, 5xx, decode) leaves the session state completely untouched.
2. **`AVDB/Views/Detail/MovieDetailView.swift` — `reloadDetail()`** now calls `appState.revalidateCredential()` instead of `appState.markNeedsReauth()`. That was the view's only marking call (the other `vm.isAuthError` use is just the 「去登录」 button in the page's own error state). The view now contains no `markNeedsReauth()` call at all.

## What did NOT change

- **The Build 327 policy, byte-identical.** `markNeedsReauth()` still retains the stored token, drops only the cached profile presentation, and never calls `logout()`/`setToken(nil)`; `resumeValidation()` still routes a profile-endpoint HTTP 401 to needsReauth; explicit `logout()` is still the only path that clears the credential. Build 338's manual exit in the needsReauth/restoring states is untouched.
- **The detail page's own error UI.** `vm.isAuthError` is computed exactly as before, the failure state still shows its message, 「重试」 and (for auth-class errors) 「去登录」 — a page whose endpoint genuinely rejects the account still looks the same. Only the session-marking side effect changed.
- **The auth classifier.** `JavDBError.isAuthenticationFailure` is unchanged; it is still what decides whether a PROFILE failure is an authentication failure.

## Visible scope for the user

Sessions no longer drop when a business endpoint returns an auth-class error while the credential still validates: open a detail page that fails with a login-flavoured error on a second account, and the account stays logged in — one quiet profile check confirms the credential, and 「我的」 keeps showing the account. If the credential is truly dead, the profile check fails authentication and the session is marked needsReauth exactly as before, with the same re-login path (and Build 338's manual exit in that state). A detail page whose endpoint genuinely rejects that account will still show its own retry state — that is server-side per-account behaviour, and this build does not (and cannot) change it; what changes is that the rest of the app no longer treats the whole login as dead because of it.
